# План развития

Проект существует ради практики DevOps. Приложение — это то, **на чём**
практиковаться; всё интересное начинается с этапа 3.

Правило движения: **не переходить к следующему этапу, пока предыдущий не
запускается и не проверен.** Половина боли в эксплуатации возникает от того,
что несколько слоёв собрали разом и теперь непонятно, какой из них сломан.

---

## ✅ Этап 0. Фундамент — сделано

Каркас репозитория, `pyproject.toml`, ruff, mypy в строгом режиме,
pre-commit, `Makefile` как единая точка входа.

**Почему Makefile важен:** на этапе 4 CI будет вызывать ровно те же цели,
что ты вызываешь руками. Пока команды живут только в твоей истории bash,
пайплайн неизбежно начнёт делать что-то немного другое.

## ✅ Этап 1. Ядро — сделано

Модели, миграции Alembic, аутентификация по JWT, CRUD счетов, категорий
и операций, изоляция данных между пользователями, тесты на настоящем Postgres.

## ✅ Этап 2. Аналитика и интерфейс — сделано

Сводки за период, разрез по категориям, динамика, месячные бюджеты.
Веб-интерфейс на Jinja и HTMX, графики без внешних библиотек.

## Этап 3. Контейнеризация

**Цель:** приложение запускается одной командой на любой машине с Docker.

- [ ] `deploy/docker/Dockerfile` — multi-stage: стадия сборки ставит
      зависимости, финальный образ содержит только рантайм.
- [ ] Непривилегированный пользователь внутри образа (`USER app`), а не root.
- [ ] `.dockerignore` — без него в контекст сборки уезжает `.venv` и `.git`,
      и сборка идёт минутами вместо секунд.
- [ ] `deploy/compose/docker-compose.yml` — приложение + Postgres, с
      `depends_on: condition: service_healthy`.
- [ ] Миграции отдельным шагом (`command: alembic upgrade head` в init-контейнере),
      а не в старте приложения. Иначе при трёх репликах три пода одновременно
      начнут менять схему.
- [ ] `HEALTHCHECK` в образе, указывающий на `/health`.

**Разберись по пути:** почему порядок инструкций в Dockerfile влияет на время
пересборки (слои и кеш); чем `COPY` отличается от `ADD`; почему `pip install`
идёт до `COPY app/`.

**Готово, когда:** `docker compose up` на чистой машине поднимает рабочее
приложение, а `docker images` показывает размер меньше 250 МБ.

## Этап 4. CI

**Цель:** ни одно изменение не попадает в main непроверенным.

У тебя на машине уже крутится GitLab CE и gitlab-runner — логично делать CI
именно там, а не в GitHub Actions.

- [ ] `.gitlab-ci.yml` со стадиями `lint → test → build`.
- [ ] Postgres как `services:` в джобе тестов; `TEST_DATABASE_URL` через
      переменные окружения.
- [ ] Кеш `.venv` или pip между запусками — иначе каждый пайплайн ставит
      зависимости заново.
- [ ] Сборка образа и push в реестр GitLab (`$CI_REGISTRY_IMAGE`), тег по
      commit SHA, а не только `latest`.
- [ ] Защита ветки main: merge только при зелёном пайплайне.

**Разберись по пути:** чем artifacts отличаются от cache; почему тег `latest`
в проде — источник неповторимых инцидентов.

**Готово, когда:** merge request с ошибкой в коде не может быть влит.

## Этап 5. Наблюдаемость

**Цель:** при проблеме ты смотришь на графики, а не гадаешь.

- [ ] Структурированные логи в JSON (`structlog`) вместо текста; в каждой
      записи — `request_id`, чтобы связать строки одного запроса.
- [ ] Middleware, проставляющий `X-Request-ID`.
- [ ] `/metrics` для Prometheus: `prometheus-fastapi-instrumentator`.
- [ ] Prometheus + Grafana в compose.
- [ ] Дашборд с четырьмя золотыми сигналами: RPS, доля ошибок, задержка
      (p50/p95/p99), насыщение (пул соединений к базе).
- [ ] Алерт: доля 5xx выше 1% пять минут подряд.

**Разберись по пути:** почему среднее время ответа бесполезно, а перцентили —
нет; чем гистограмма отличается от counter и gauge.

**Готово, когда:** ты можешь сказать «вчера в 14:20 p95 вырос до 2 секунд из-за
отчётов» — глядя на график, а не на логи.

## Этап 6. Фоновый воркер

**Цель:** появляется второй тип процесса — и с ним новый класс проблем.

- [ ] Модель `RecurringTransaction`: зарплата, аренда, подписки.
- [ ] Воркер, который раз в сутки материализует наступившие регулярные операции.
- [ ] **Идемпотентность**: повторный запуск за тот же день не должен создавать
      дубли. Это главное, ради чего этап затевается.
- [ ] Отдельный контейнер и отдельная точка входа.
- [ ] Метрики воркера: время последнего успешного прогона, число созданных
      операций, число ошибок.

**Разберись по пути:** почему «раз в сутки по cron» и «ровно один раз» — не
одно и то же; что произойдёт, если воркер упадёт на середине.

## Этап 7. Kubernetes

**Цель:** приложение живёт в кластере и переживает падение пода.

- [ ] Локальный кластер: `kind` или `minikube`.
- [ ] Манифесты: Deployment, Service, Ingress, ConfigMap, Secret.
- [ ] Проверки: `livenessProbe` → `/health`, `readinessProbe` → `/ready`.
      Разница между ними — на этом этапе она перестаёт быть теорией:
      неверно настроенный liveness с проверкой базы устроит бесконечный
      перезапуск подов при недоступном Postgres.
- [ ] `resources.requests` и `limits` — без них планировщик не знает, сколько
      места занимает под.
- [ ] Миграции как `Job` или `initContainer`.
- [ ] Postgres не в кластере, а рядом (managed или отдельная VM). Stateful в
      Kubernetes — отдельная большая тема, не смешивай её с первой попыткой.
- [ ] Затем упаковать всё в Helm-чарт с `values.yaml` на окружение.
- [ ] Убей под во время работы (`kubectl delete pod`) и убедись, что запросы
      не потерялись.

## Этап 8. Инфраструктура как код и доставка

**Цель:** окружение воспроизводится из репозитория, а не из памяти.

- [ ] Terraform: VPS, сеть, файрвол, managed-база.
- [ ] Состояние Terraform в удалённом бэкенде, не в локальном файле.
- [ ] CD: деплой из пайплайна по тегу; на первых порах — ручное подтверждение.
- [ ] Секреты: SOPS или Vault. `.env` в репозитории — нет.
- [ ] Автоматические бэкапы базы **и проверка восстановления**. Бэкап, из
      которого ни разу не восстанавливались, бэкапом не является.
- [ ] Нагрузочный тест (k6): найди, на каком RPS ломается, и почему именно там.

## Что осознанно НЕ сделано в первой версии

Это не забытое, а отложенное — с причинами. Пункты годятся как задачи, когда
захочется поработать над самим приложением, а не над обвязкой.

| Чего нет | Почему отложено |
|---|---|
| Мультивалютность | Нужны курсы на дату операции и решение, в какой валюте считать отчёты. Отдельная задача, а не флажок. |
| Помесячные лимиты («в декабре больше») | Требует таблицы периодов. Пользы мало, пока нет истории за год. |
| Иерархия категорий в отчётах | Поле `parent_id` есть, свёртки по дереву нет. |
| Импорт выписки из банка | Самая полезная фича для реального использования — и самая объёмная: у каждого банка свой CSV. |
| Восстановление пароля | Нужен SMTP и одноразовые токены. |
| Ограничение частоты запросов (rate limiting) | Появится вместе с публичным доступом на этапе 8. |

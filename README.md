# Финансовый трекер

Учёт доходов и расходов, анализ трат по категориям и контроль месячных бюджетов.

Приложение написано как **сервис, а не как скрипт**: HTTP API, отдельная база,
миграции, пробы состояния, тесты. Это сделано намеренно — проект задуман как
полигон для практики DevOps, и на скрипте с CSV-файлом отрабатывать нечего.

```
┌─────────────┐     HTTP      ┌──────────────────────┐    SQL    ┌────────────┐
│  Браузер    │ ────────────► │  FastAPI             │ ────────► │ PostgreSQL │
│ (Jinja+HTMX)│               │  ├── /api/v1  (JSON) │           │     16     │
└─────────────┘               │  ├── /       (HTML)  │           └────────────┘
┌─────────────┐               │  └── /health /ready  │                 ▲
│ curl / API  │ ────────────► │                      │                 │
└─────────────┘               └──────────────────────┘            Alembic
```

## Быстрый старт

```bash
make install     # venv + зависимости
cp .env.example .env
make db-up       # Postgres в Docker (порт 5433)
make migrate     # накатить схему
make demo        # необязательно: полгода демо-данных
make run         # http://localhost:8000
```

Демо-вход: `demo@local` / `demo12345`. Документация API: <http://localhost:8000/docs>.

`make help` покажет все доступные команды.

## Что умеет

**Учёт.** Счета (наличные, карта, вклад, кредитка), доходы, расходы и переводы
между своими счетами. Остаток по счёту не хранится в базе, а всегда считается
из начального остатка и истории операций — так он физически не может разойтись
с фактами.

**Аналитика.** Сводка за период, разрез по категориям с долями, динамика по
дням/неделям/месяцам/годам, норма сбережений. Переводы во всех отчётах
исключаются: перекладывание денег с карты в кошелёк не является ни доходом,
ни расходом.

**Бюджеты.** Месячный лимит на категорию расходов, прогресс с предупреждением
при приближении к лимиту и при перерасходе.

**Многопользовательский режим.** Регистрация, JWT. Данные пользователей
изолированы; запрос к чужому объекту возвращает 404, а не 403 — иначе по коду
ответа можно было бы перебором выяснить, какие записи существуют у других.

## Структура

```
app/
├── main.py             сборка приложения
├── config.py           настройки из переменных окружения
├── db.py               подключение к базе, выдача сессий
├── security.py         хеширование паролей, выпуск и проверка JWT
├── palette.py          палитра графиков (см. «Цвета» ниже)
├── models/             таблицы (SQLAlchemy)
├── schemas/            контракт HTTP-слоя (Pydantic)
├── services/           бизнес-логика — не знает про HTTP
├── api/v1/             REST-эндпоинты
├── web/                серверный рендеринг: маршруты, шаблоны, стили
└── observability/      логирование, /health, /ready

alembic/versions/       миграции схемы
deploy/compose/         Postgres для разработки
scripts/seed_demo.py    демо-данные
tests/
├── unit/               без базы: пароли, форматирование, валидация
└── integration/        с реальным Postgres: API, отчёты, веб-страницы
docs/ROADMAP.md         план развития по этапам
```

Слои разделены по одному правилу: **`services/` ничего не знает о HTTP.** Он
бросает доменные исключения, а превращает их в коды ответа единственный модуль
`api/exception_handlers.py`. Благодаря этому ту же логику можно вызвать из
воркера, скрипта или теста, не таща за собой FastAPI.

## Команды

| Команда | Что делает |
|---|---|
| `make install` | venv и зависимости |
| `make db-up` / `db-down` / `db-reset` | Postgres в Docker |
| `make migrate` | накатить миграции |
| `make migration m="..."` | сгенерировать новую миграцию |
| `make run` | запустить с автоперезагрузкой |
| `make demo` | наполнить базу демо-данными |
| `make test` / `test-cov` | тесты |
| `make lint` / `fmt` / `typecheck` | качество кода |
| `make check` | всё сразу — то же самое будет делать CI |

## Технические решения

**Суммы — `Decimal`, не `float`.** В float `0.1 + 0.2 == 0.30000000000000004`;
на тысяче операций отчёт разъезжается с реальностью. В базе — `NUMERIC(14,2)`.

**Перевод — одна строка, а не две.** У операции есть `account_id` (откуда) и
`counter_account_id` (куда). Вариант «две строки, расход и доход» требует их
синхронного создания и удаления и разъезжается при любом сбое на середине.

**Правила продублированы в Pydantic и в CHECK-констрейнтах.** Схема даёт
пользователю понятную ошибку 422, а констрейнт гарантирует, что некорректная
строка не появится никаким другим путём — через psql, миграцию или будущий
воркер.

**Цвета категорий хранятся как номер слота палитры, а не HEX.** У слота два
значения — для светлой и тёмной темы. Палитра из восьми оттенков подобрана так,
что соседние цвета различимы при основных видах дальтонизма; в графиках
категории сверх восьмой сворачиваются в «Остальное». Цвет нигде не является
единственным носителем смысла: рядом всегда есть подпись.

**Пароль проверяется даже для несуществующего email.** Иначе ответ приходит
заметно быстрее, и по времени отклика можно перебрать, какие адреса
зарегистрированы.

**Тесты работают с настоящим PostgreSQL.** Половина логики приложения — это SQL
(`date_trunc`, `CHECK`, `ON DELETE`, агрегаты). На SQLite такие тесты были бы
зелёными и не проверяли бы ничего. Схема в тестах накатывается миграциями, так
что каждый прогон заодно ловит рассинхрон между моделями и миграциями.
